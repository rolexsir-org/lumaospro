# Wallpaper, widgets, and lock-screen integration

**Date:** 2026-10-28
**Scope:** Follow-up on branch `arena/f6f4e2b5-lumaospro`; the earlier production-polish work remains in the checkout. This is an engineering report, not a claim of a completed Android build or device verification.

## Audit and implementation

- **Wallpaper Studio:** Source review caught and fixed a bounds-only decode bug in the new implementation: Android intentionally returns a null bitmap when only reading dimensions, so treating that null as a missing stream prevented every preview and application. Three Android bitmap/storage regression tests were added but could not be run here. Home's wallpaper action and Settings now open a separate Compose surface. It reuses the three existing Aurora, Zen, and Void assets and provides categories, image previews, persisted favorites, and the Android document picker for photos. The original system picker is still available for OEM sources and live wallpapers. No live-wallpaper service or synthetic artwork was added.
- **Photo handling:** Only a chosen image is copied into app-private storage; no broad photo permission is requested. The store admits at most 12 images of at most 12 MiB each, validates source dimensions (maximum edge 20,000 and 100 million pixels), samples previews and wallpaper bitmaps, applies EXIF orientation, serializes imports, and removes abandoned temporary copies on the next import. Wallpaper application uses at most a 2,560-pixel edge and five million decoded pixels; this trades some resolution for a bounded allocation on low-memory devices. A delete confirmation removes only the Luma copy, not the original or an already-set system wallpaper. Copies can retain embedded EXIF metadata, including location.
- **Application and theme:** `WallpaperManager` receives an explicit home, lock, or combined target after the user chooses it. The app checks system support/policy, handles failures, and does not request system backup for user photos. Cropping and whether separate lock wallpaper is supported remain Android/OEM decisions. A wallpaper write already handed to Android may finish after the Studio activity is recreated; that lifecycle behavior is unverified. The existing `WallpaperColorSource` already drives Chroma from the system home wallpaper on API 27+. The studio additionally previews extracted colors and offers an explicit accent override (API 26 uses a sampled average); it does not silently replace a selected theme. A separate action changes only the existing Home backdrop preference to `WALLPAPER`, since Pure and Liquid may otherwise cover a newly-set system wallpaper. Appearance Studio remains the place to change or reset that backdrop/accent; a later experience-profile change can also replace those appearance choices.
- **Music:** `Luma Glass Music` is a normal `AppWidgetProvider`, using the existing host and layout model. An explicit disclosure precedes Android's optional notification-listener settings. The listener is protected by `BIND_NOTIFICATION_LISTENER_SERVICE`; the playback-control receiver is non-exported and uses immutable, explicit pending intents. The app queries active media sessions, chooses a playing session first, then a paused one, with Android priority breaking ties, and registers callbacks for up to 16 sessions. It renders available metadata/artwork, hides unsupported transport actions, rechecks the selected session and advertised action before dispatch, and handles no access, missing sessions, unknown metadata, and revoked/disconnected access. The host's `Chronometer` advances known normal-speed playback; paused positions are static and unsupported/unknown progress is hidden. A single end-of-track callback is scheduled only while the process is alive; there is no app-side periodic playback poll. Media-session callbacks and artwork jobs are released when no widget remains or access is lost; the theme observer remains while a music widget exists so its permission/empty state can follow theme changes. Artwork is bounded to 192 pixels for `RemoteViews`; content-URI reads are bounded to 4 MiB. The system may still retain/cache the widget's last display and may kill/restart the process.
- **Battery:** The old battery data source and dial existed, but the dial/readout are hidden in the current Home composition. A real `Luma Glass Battery` widget was added instead of treating that hidden view as a visible widget. It reads Android's sticky battery data and shows an unavailable state for invalid/missing data, differentiates full and charging, and displays the time it last checked. While Luma Home is started it reuses the existing battery receiver. When Home is not active, the provider relies on Android's 30-minute-or-longer widget update; Android can delay it. No separate persistent service or global power-change broadcast was added.
- **Existing widgets:** Home already displays a real clock/date and hosts third-party Android widgets with binding, sizing, and local layout persistence. No duplicate clock, fabricated weather, calendar, or photo widget was added. Those three widget types remain absent from Luma itself; third-party providers remain available. Weather and calendar would require a reliable source and additional permission/product decisions; a photo widget needs its own persistence, restore, and privacy design.

## Lock screen and API boundary

The minimum is Android 8.0/API 26. `FLAG_SYSTEM`/`FLAG_LOCK` wallpaper targeting is available from API 24; wallpaper color extraction is available from API 27. Android owns keyguard, PIN/password/biometrics, system notifications, and the system media surface. The implementation does not use `showWhenLocked`, keyguard dismissal, device administration, accessibility, an overlay, or a replacement lock-screen activity. It does not claim to change lock-screen clocks, notifications, controls, or OEM layouts. A third-party player's Android media session/notification may be shown by the system lock screen under that device's own rules; Luma does not publish or replace that system surface. The new widgets declare `home_screen` only.

## Storage, restore, and privacy boundaries

Android backup/transfer includes the existing DataStore settings, including wallpaper-favorite identifiers, but excludes the private photo files. After a device restore, favorites for missing photos are not shown; reimporting the original creates a new photo entry and requires marking it favorite again. The existing manual JSON backup excludes wallpaper favorites, photo files, and app-widget IDs; restoring it leaves current wallpaper favorites alone. Android's own wallpaper storage and OEM backup behavior are separate from Luma's files.

The first-party providers have no per-widget configuration to migrate and implement provider restoration callbacks. **The existing Luma widget host does not handle `ACTION_APPWIDGET_HOST_RESTORED` and does not remap restored host IDs in saved layouts.** A cross-device Android restore can therefore leave widget placements unavailable; users may need to re-add widgets. Local layout serialization is tested, but system host restore, permissions, and provider binding are not verified. Fixing host remapping safely across all profile layouts and partial restores remains release work; no speculative deletion of user placements was added here.

Android notification access can expose all notifications, not just music. The listener does not inspect or persist notification contents; it temporarily processes media-session metadata and artwork, while Android/widget hosts may cache displayed details. The revised in-app summary and `PRIVACY_POLICY_DRAFT.md` disclose this. Publisher/legal review, a public privacy-policy URL, and accurate Play Data safety answers remain required.
